# Teardown MCP: start here

An MCP server (Rust, `server/`) plus an in-game mod (`mod/`, "MCP Bridge") that let an MCP client
drive a running Teardown 2.x game, and a skill (`skill/teardown-modding/`) that holds what was
measured about the engine. Main user of all three: Claude sessions developing Teardown mods
(the user's own is Mors Longa Revival, `C:\Projects\Mors Longa`).

Read `README.md` for the protocol, `skill/teardown-modding/references/quirks.md` for engine
facts, `references/bridge.md` for the tools.

## Layout

| Path | What |
|---|---|
| `server/src/main.rs` | MCP protocol (hand-written JSON-RPC over stdio), tool list and dispatch |
| `server/src/bridge.rs` | Command file writing, reading replies from savegame.xml or the game logs, waiting logic |
| `server/src/mptest.rs` | Starting / stopping the local multiplayer test windows |
| `server/src/shot.rs` | Window screenshot (raw Win32 FFI) |
| `server/src/diag.rs` | Diagnostics from outside the game: process health, exit codes, crash reports, thread stacks and minidumps (dbghelp), GPU via nvidia-smi |
| `server/src/exe_names.rs` | Function starts from a teardown.exe's .pdata; names from the table for exactly that build |
| `server/names/*.tsv`, `server/src/name_tables.rs` | Per-build function name tables and their generated index (`tools/port_names.py`) |
| `tools/port_names.py` | Ports name tables to a new game build (README, "After a game update") |
| `server/src/input.rs` | Key presses, clicks, drags and mouse movement in the game window (`SendInput`) |
| `mod/main.lua` | The bridge: polls the command file, runs actions, writes results |
| `mod/mcp_config.lua` | Generated by the server (absolute path of the command file); not in git |
| `skill/teardown-modding/` | The skill: `SKILL.md`, `references/` |
| `playground/` | Level mod with mini-mods (buggy, target range, director, gate, custom tool, clickable menu) used to exercise the API; linked into the game as `mcp-playground` |
| `probemode/` | Global mod (no level) with a probe game mode; linked into the game as `mcp-probe-mode` |
| `tools/lua/` | Small Lua readers / helpers to run with `run_lua` `file` |
| `tools/mcp_call.py` | Call the server from a script (tests, probes) |
| `tools/probe/` | API probes whose results feed the skill; `README.md` there |
| `tools/gen_api_index.py` | Regenerates `references/api-index.md` |
| `tools/fetch_unofficial_docs.py` | Downloads the Unofficial TD Docs data (site's `gh-pages` bundle) and lists what `api-index.md` lacks; feeds `references/unofficial-docs.md` |

## How it works (the parts that are easy to get wrong)

- The game never re-reads `savegame.xml`, so commands go in through
  `%LOCALAPPDATA%\Teardown\mcp_inbox.lua`, which the mod `loadfile`s every 0.1 s.
- Replies: normal game → `savegame.mod.mcp_*` keys, read from `savegame.xml`. Multiplayer test
  (never writes the savegame) → the test window's log file, via failed `LoadSound` calls whose
  path carries the data. The server picks per call: log when a window "TD - Host" exists.
- Log replies are emitted only by the **client half** (`relayToLog`): a server-half `LoadSound`
  is replicated to every joined client.
- The command file is outside the mod folder on purpose: the multiplayer test hashes mod
  folders and kicks a client whose copy differs.
- Sides: `server`, `client`, `draw` (host's `client.draw`), `remote` (the joined client's game,
  which reads the same command file and answers in its own log).
- A command is marked started before it runs and is never run twice; reload commands answer
  first and act three polls later so the answer gets out.
- `CLIENT_ONLY` / `SERVER_ONLY` in `mod/main.lua` are guards: the engine stops a script half
  on a wrong-side call instead of raising an error. Keep them in step with the probe results.

## Working here

- Build: `cargo build --release` in `server/`. A running server locks its exe: build with
  `--target-dir target-test`, rename the old `target/release/teardown-mcp.exe`, copy the new
  one in. Sessions keep the old binary until their `teardown` MCP server is reconnected.
- The mod is linked into the game as `Documents\Teardown\mods\mcp-bridge` (a junction to
  `mod/`). A mod change needs a level reload; in the multiplayer test restart the test, since
  host and client must load the same files.
- For trying API behaviour or a bridge change in real use, the playground reloads in 2 s:
  `python tools/mcp_call.py mp_test_start '{"mod":"mcp-playground","restart":true}'`
  (add `"players":1` for the host window alone when a second player is not needed).
- Test in a built-in level, not in a heavy mod:
  `python tools/mcp_call.py mp_test_start '{"mod":"builtin-villagordon","restart":true}'`,
  then `python tools/mcp_call.py ping '{}' ping '{"side":"remote"}'`.
- Before the first bridge command after 5 minutes without an answer (or after a failed call,
  or `mp_test_stop`), `Bridge::send` runs `diag::alive_check` (window open, not hung) and
  fails at once without sending if the game is gone. `diag::windows_check` runs before any
  `side: remote` command and once a second while waiting (host window, plus the client's
  while a remote result is missing), so a crashed window ends the call at once with its exit
  code; `wait_players_except` uses it too once the client window was seen.
- A child process started by the server must not inherit its stdio (see `keep_stdio_private`):
  a client waiting for end-of-output would hang on the game.
- `send_input` takes the user's keyboard focus: say so before a run of input tests, pass
  `restore_focus: false` between consecutive calls and restore on the last.
- Single-player pause stops every callback but `client.render`: the bridge then polls from
  there (only after 30 renders without a tick, so never in normal play or the multiplayer
  test), runs `side: client` commands and answers other sides with a "paused" error;
  `SetPaused(false)` from there resumes (verified 2026-11-21), as does a `send_input` click on
  Continue. The multiplayer test does not pause. Do not quit to the menu or call `StartLevel` with an
  unproven path: the bridge cannot recover and the user has to click.
- The game updates without changing its version string: compare native offsets only within
  one teardown.exe build (PE timestamp). After an update, save both exes' code
  (`save_game_code`) and port the name tables (`tools/port_names.py`, README "After a game
  update"), then rebuild. The saved code (`%LOCALAPPDATA%\Teardown\mcp_code\`) is the game's:
  never copy it into the repository or share it.
- Steam will not start the normal game while a multiplayer test window is open (it counts as
  Teardown running): stop the test first. `dump_game` and `perf_sample` were tested on the
  multiplayer test; `game_health` remembers processes per server process (a new
  `tools/mcp_call.py` run starts fresh).
- New engine facts go into `skill/teardown-modding/references/quirks.md` with date, game
  version and how they were measured. Say "not verified" where that is the case.
- Lua files are LF. `mod/mcp_config.lua` and build output are not committed.
- Git: commit and push only when the user asks. Remote: `OfficialSirH/teardown-mcp` (public).

## The user

Software engineer, new to Lua, Teardown modding and skills. Tests in the game themself and
watches the windows: say before starting or restarting game windows, and do not leave a call
waiting silently for minutes.
